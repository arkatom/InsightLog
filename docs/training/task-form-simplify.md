# 実習: 曖昧な要望を具体化して解く

## 受け取った要望

こんな要望を受け取ったことありませんか？ **わざと曖昧にしてある要望** を、自分で具体化してから Claude Code に渡し、実装・動作確認までやりきる練習です。

> タスクの記録をもっと簡単にしてください。毎回要素を選び直すのが面倒です。

この要望をそのまま AI に渡しても良い結果は出ません。**自分で「何が面倒で、どう解決するか」を具体化してから** 渡します。

## 🎯 理想の完成形

前回選択した **AI ツール** と **カテゴリ** が、次のタスク記録時に **初期値として再表示される** 状態。

この状態に持っていくために、曖昧な Issue をどう具体化するかを自分で考えて、指示文として書き出します。

## ゴール

- 曖昧な Issue を具体的な指示に変換する経験を積む
- 「どのファイルを変えるか」は AI に任せる（自分で考えなくていい）
- InsightLog に記録まで完了する

## 進め方（35分）

### Phase 1 — 思考時間（7分・各自）

**手は動かさない。頭で考える時間です。**

以下を順に考えてください：

1. **何が面倒なのか？**
   - カテゴリを毎回選ぶのが面倒？
   - AI ツール選択が面倒？
   - 時間入力が面倒？
   - 振り返りメモを書くのが面倒？

2. **どう改善するのか？**
   - 前回の値を保持する？
   - よく使うプリセットを作る？
   - 入力欄を減らす？
   - デフォルト値を賢くする？

3. **指示文として書き出す**

    Claude Code に渡せる粒度の文章にする。例:

    ```
    TaskForm で、前回選択したカテゴリと AI ツールを
    次回の初期値にしてほしい。
    ```

    対象（TaskForm）と動作（初期値にする）を明確に。

> **ヒント**: 完璧な解決案じゃなくていいです。「何が面倒で、どうしたいか」を1文で言えれば OK。

### Phase 2 — Claude Code に渡す（20分・各自）

1. Phase 1 で書いた指示文を Claude Code に渡す
2. 実装が返ってきたらブラウザで動作確認（`npm run dev` が動いている前提）
3. 思った通りでなければ、さらに指示を追加して修正
4. いい感じになったらここでいったん完了

> **大事**: 完成が目的ではありません。**具体化する過程** と **指示を出して動作確認するサイクル** を経験することが学びです。

### Phase 3 — InsightLog に記録（5分）

InsightLog のタスク記録フォームに以下を入力：

| 項目 | 何を書くか |
|------|-----------|
| タスク名 | 例: タスク記録フォームの改善 |
| AIツール | Claude |
| 所要時間 | 実測値 |
| AI 未利用時の推定 | 自力だったら何分かかるか |
| 手戻り回数 | 指示のやり直し回数 |
| カテゴリ | 実装 / 調査 / レビュー など（複数選択可） |
| 振り返りメモ | **特に大事**: 最初の指示で何が足りなかったか、具体化した後に何が変わったか |

## プロンプト改善 3 段階例

実習で書く指示は、**3 段階のレベル感**を意識すると差分が見えやすくなります。同じ要望「タスクの記録をもっと簡単にしてください」を例に、**悪い指示 → 良い指示 → さらに良い指示** のグラデーションを示します。

### Level 1 — 悪い指示（受け取った要望そのまま）

```
タスクフォーム簡単にして
```

- **何が問題か**: 対象（どの画面の何）・粒度（何を残し、何を消すか）・完了判定（どうなれば OK か）が一切ない
- **AI の反応**: 「どのフィールドを削りますか?」と質問が返る、または想定外の改修（フィールドを 5 個削るなど）が走る
- **手戻り**: 1-3 ターンの追加質問で時間消費

### Level 2 — 良い指示（具体化を 1 段階）

```
apps/InsightLog/src/components/task/TaskForm.tsx で、
前回選択したカテゴリと AI ツール（どちらも複数選択チェックボックス）の
セットを次回の初期値にしたい。
保存場所は IndexedDB (Dexie) の settings テーブル。
既存の useSettings() フックを使う。
```

- **改善点**: 対象ファイル（`TaskForm.tsx`）・UI 形式（複数選択チェックボックス）・動作（初期値保持）・データ層（Dexie の settings テーブル + 既存フック）が明示
- **AI の反応**: 質問なしで実装を始める。1 回の往復で動く版が出る
- **残る曖昧**: 既存テストを壊すか、初回起動時の挙動、schema 変更の影響範囲が未定義

### Level 3 — さらに良い指示（品質保証 + 副次配慮を追加）

```
apps/InsightLog/src/components/task/TaskForm.tsx で、
前回選択したカテゴリと AI ツール（どちらも複数選択チェックボックス）の
セットを次回の初期値にしたい。
保存場所は AppSettings (apps/InsightLog/src/types/settings.ts) に
lastSelectedAITools: string[] と lastSelectedCategories: string[] を追加し、
既存の useSettings().updateSettings() で部分更新する。

制約:
- 初回起動時（過去ログなし）は両方とも空配列（未選択状態）で表示すること
- 既存のユニットテスト（src/tests/unit/）を破壊しないこと
- 新規ロジックに対するテストを 1 件以上追加（「保存後、useSettings().settings.lastSelectedAITools が更新される」）
- Dexie schema 変更は追加のみ（既存ユーザーの tasks / settings データは保持）
- 設計判断は apps/InsightLog/CLAUDE.md のアーキテクチャ判断セクションに従う
- 動作確認: npm run dev でブラウザ確認、ページリロード後・ブラウザ再起動後に初期値が保持されているか
```

- **改善点**: Acceptance Criteria 相当（6 項目の制約）・既存資産保護・設計参照先・動作確認手順を明記
- **AI の反応**: 1 回で「動く・テスト付き・既存破壊なし・マイグレーションあり」の PR が出やすい
- **残るリスク**: KPI（入力 30 秒 → 15 秒）と運用 KPI 接続の議論は完成形の Issue (`task-form-simplify.issue.md`) で扱われている

### この 3 段階を見て学ぶこと

- **Level 1 → Level 2**: 「対象 / UI 形式 / 動作 / データ層 / 既存フック」を書き出すだけで AI の往復が激減
- **Level 2 → Level 3**: 「制約 / 完了判定 / 既存資産保護 / マイグレーション方針」を添えると AI の出力が安定し、受講者がレビューしやすくなる
- **逆方向の罠**: Level 3 を書こうとして「完璧主義」で 30 分も悩むなら、まず Level 2 で投げて Claude Code の質問に答える方が速い
- **Phase 1 との関係**: Phase 1 で受講者が書くのは Level 1 → Level 2 の橋渡しで十分（**1 文 OK**）。Level 3 は実装後の答え合わせ・AI 反復の効率化を学ぶための到達例なので、Phase 1 で完璧に書く必要はない

具体例の完成形は [`apps/InsightLog/docs/specs/task-form-simplify.issue.md`](../specs/task-form-simplify.issue.md) を参照してください（Level 3 とほぼ同等の情報量を Markdown Issue 形式で構造化）。

## 詰まったら

- **何が面倒か思いつかない**: 実際にタスク記録を1回やってみる。手を動かすと不満が見える
- **どう指示していいか分からない**: まず1文で書いてみる。Claude Code が質問を返してくれる
- **実装が思った通りにならない**: 最初の指示と今の指示を見比べて、何が曖昧だったか言語化する
- **時間内に終わらない**: 完成が目的ではない。そこまでの過程を Phase 3 で記録する

## 完成の定義

- [ ] 自分で Issue を具体化した（Phase 1）
- [ ] Claude Code に指示を渡して変更が入った（Phase 2）
- [ ] ブラウザで変更を確認した
- [ ] InsightLog に振り返りメモまで書いて記録した（Phase 3）
